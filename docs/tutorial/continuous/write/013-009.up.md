## 第 2 步：platform_governance_grant

插入位置：第 1 步代码之后，紧接追加；完成稿约第 4 行。

本步声明：`CREATE TABLE platform_governance_grant (`。

**这一段为什么这样写：** Account唯一平台治理任免事实，独立epoch保证撤权后旧治理准入失效。

**先理解这一张表，再写下面的完整 SQL：**

| 列 | 数据库定义 | 保存什么、为什么需要 |
| --- | --- | --- |
| <code>user_id</code> | <code>BIGINT UNSIGNED NOT NULL</code> | 关联的账号编号；昵称会改变，关系关联使用稳定编号。 |
| <code>epoch</code> | <code>BIGINT UNSIGNED NOT NULL DEFAULT 1</code> | 本记录的代次，推进后旧代次请求不能继续作用于新状态。代次与幂等操作号承担不同职责。 |
| <code>revision</code> | <code>BIGINT UNSIGNED NOT NULL DEFAULT 1</code> | 本对象的修订计数，用于发现读取后发生的并发变化；不能用创建时间代替。 |
| <code>state</code> | <code>VARCHAR(16) CHARACTER SET ascii COLLATE ascii_bin NOT NULL DEFAULT &#x27;CLOSED&#x27;</code> | 本表对象的生命周期或处理状态；下方 CHECK 限定可写值，业务状态机决定哪些转移可发生。 |
| <code>changed_operation_id</code> | <code>VARCHAR(96) CHARACTER SET ascii COLLATE ascii_bin NOT NULL</code> | 推进当前修订的原操作号，恢复时认回是哪次修改已提交。 |
| <code>updated_at</code> | <code>DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)</code> | 最近一次记录更新的时间，用于观察推进情况，与初次创建时间分开。 |

键与约束：

- <code>PRIMARY KEY(user_id)</code>：这一列组合唯一定位本表记录；同一组合不能插入第二行。组合键的所有列都参与身份判断。
- <code>CHECK (epoch&gt;0 AND revision&gt;0)</code>：把这里列出的状态或数值范围交给数据库再次约束，业务代码校验之外再防止非法值落库。
- <code>CHECK (state IN (&#x27;ACTIVE&#x27;,&#x27;REVOKING&#x27;,&#x27;CLOSED&#x27;))</code>：把这里列出的状态或数值范围交给数据库再次约束，业务代码校验之外再防止非法值落库。

NOT NULL 要求写入时提供值或使用声明的默认值；NULL 表示该事实尚不存在，不能随意以空字符串代替。时间按连接的 UTC 约定处理。

<!-- write-step: 2 bytes=228:754 -->
````sql

CREATE TABLE platform_governance_grant (
  user_id BIGINT UNSIGNED NOT NULL,
  epoch BIGINT UNSIGNED NOT NULL DEFAULT 1,
  revision BIGINT UNSIGNED NOT NULL DEFAULT 1,
  state VARCHAR(16) CHARACTER SET ascii COLLATE ascii_bin NOT NULL DEFAULT 'CLOSED',
  changed_operation_id VARCHAR(96) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
  updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY(user_id),
  CHECK (epoch>0 AND revision>0),
  CHECK (state IN ('ACTIVE','REVOKING','CLOSED'))
) ENGINE=InnoDB;
````
